Die Nutzung des massively-Crates verändert die Architektur deines Raymarchers fundamental von einem klassischen pixel-zentrierten (Gather)-Ansatz zu einer daten- und stream-zentrierten (Scatter/Map)-Pipeline. [1] (https://users.rust-lang.org/t/massively-gpu-parallel-algorithms-library-like-nvidias-thrust/140820), [2] (https://github.com/massively-labs/massively)
In herkömmlichen Implementierungen berechnet jeder Thread einen kompletten Sichtstrahl von Anfang bis Ende. Dies führt zu massiver Warp-Divergenz, da Threads, die leeren Raum durchqueren, sofort fertig sind, während Threads im dichten Nebel hunderte mathematische Schritte ausführen. Die GPU-Kerne müssen aufeinander warten, was die FPS einbrechen lässt.
Durch den "Composition-First"-Ansatz von massively zerlegen wir das Problem mithilfe von Lazy Iterators und optimierten Parallel-Primitives. [1] (https://github.com/akiradeveloper/pi-monte-carlo)

Der Performance-Hebel durch massively

1. Eliminierung von Warp-Divergenz: Wir wandeln die 2D-Bildschirmfläche in einen flachen DeviceVec aus Strahlen um. Mittels massively::vector::map führen wir homogene, gleich lange Teilschritte für alle aktiven Strahlen gleichzeitig aus.
2. Stream Compaction (Early Ray Termination auf globaler Ebene): Anstatt dass inaktive Threads in einem Warp Leerlaufzyklen erzeugen, filtert massively::vector::copy_where tote Strahlen (deren Transmission 0.0 erreicht hat oder die das Volumen verlassen haben) global aus dem Stream heraus. Die Arbeitslast schrumpft mit jedem Schritt.
3. Zero-Copy Transformationen via Zip: Mit zip3 verknüpfen wir Strahlen-Ursprünge, Richtungen und akkumulierte Farben zu einem einzigen logischen Datenstrom, ohne jemals Zwischenpuffer im VRAM zu materialisieren.

Schritt 1: Der homogene Raymarch-Schritt als UnaryOp

Wir schreiben eine atomare Operation, die für jeden Strahl exakt einen einzigen Volumenschritt (inklusive Jitter, Absorption und Phasenfunktion) berechnet.
rust
use massively::op::UnaryOp;

pub struct SingleVolumeStep {
    pub step_size: f32,
    pub time: f32,
    pub fog_density: f32,
}

#[cubecl::cube]
impl UnaryOp<RayState> for SingleVolumeStep {
    type Output = RayState;

    fn apply(mut ray: RayState) -> RayState {
        // Wenn der Strahl bereits absorbiert ist, überspringe teure Berechnungen
        if ray.transmittance < 0.001 {
            ray.transmittance = 0.0;
            return ray;
        }

        // Berechne die aktuelle Position für diesen spezifischen globalen Schritt
        let current_pos = ray.origin;

        // Nutze deine bestehende Register-Bound Dichtefunktion
        let sample = get_volumetric_data(current_pos, self.time, 1.5);

        if sample.density > 0.0 {
            let opacity = sample.density * self.step_size * self.fog_density;
            
            // In-Scattering & Emission aufschlagen
            let total_radiance = sample.emission; // Vereinfacht für das Sample
            ray.accum_color = ray.accum_color.add(total_radiance.scale(opacity * ray.transmittance));
            
            // Transmission reduzieren
            ray.transmittance = ray.transmittance * (1.0 - opacity);
        }

        // Strahl für den nächsten globalen Pipeline-Schritt nach vorne schieben
        ray.origin = ray.origin.add(ray.dir.scale(self.step_size));
        ray
    }
}

Schritt 2: Stream-Filterung via PredicateOp

Dieser Operator entscheidet, welche Strahlen noch aktiv rechenberechtigt sind. Tote Strahlen fliegen aus dem aktiven GPU-Register-Pool.
rust
use massively::op::PredicateOp;

pub struct ActiveRayFilter;

#[cubecl::cube]
impl PredicateOp<RayState> for ActiveRayFilter {
    fn apply(ray: RayState) -> u32 {
        // massively MFlag: 0 ist false, 1 (oder ungleich 0) ist true
        if ray.transmittance > 0.001 { 1 } else { 0 }
    }
}

Schritt 3: Die Haupt-Streaming-Schleife auf dem Host (CPU)

Anstatt einen monolithischen Kernel zu launchen, orchestriert die CPU die Ausführung über den massively::Executor. Dank des Stream-Verfahrens terminiert die GPU Berechnungen für leere Pixel sofort, wodurch die FPS dramatisch steigen. [1] (https://users.rust-lang.org/t/massively-gpu-parallel-algorithms-library-like-nvidias-thrust/140820), [2] (https://github.com/massively-labs/massively)
rust
fn run_massively_raymarcher(
    exec: &Executor<WgpuRuntime>,
    init_rays: Vec<RayState>,
    max_steps: u32,
    step_size: f32,
    time: f32,
    fog_density: f32,
) -> Result<Vec<RayState>, massively::Error> {
    // 1. Initialisiere die Daten auf dem Device
    let mut active_rays = exec.to_device(&init_rays);
    
    let step_op = SingleVolumeStep { step_size, time, fog_density };

    // 2. Iteriere über die Distanzebenen
    for _step in 0..max_steps {
        // Kontrolliere die verbleibende Anzahl aktiver Strahlen
        if active_rays.len() == 0 {
            break;
        }

        // Transformiere alle Strahlen homogen um eine einzige Distanzstufe (ALU-gebunden)
        let stepped_rays = map(exec, active_rays.slice(..), step_op)?;

        // 🟢 DER FPS-BOOSTER: Stream Compaction
        // Wir filtern alle absorbierten/toten Strahlen heraus. 
        // Das verkleinert den Vektor für die nächste Iteration im GPU-Speicher (Zero-Copy)!
        active_rays = copy_where(exec, stepped_rays.slice(..), ActiveRayFilter)?;
    }

    // 3. Zurückholen der verbleibenden (oder finalisierten) Daten auf den Host
    exec.to_host(&active_rays)
}

Warum das deine FPS massiv steigert:

• Perfekte Auslastung der SIMD-Glieder (Warp-Symmetrie): Jeder Thread innerhalb eines 32er oder 64er Blocks auf der GPU tut in diesem Moment exakt dasselbe. Es gibt keine Verzweigungen innerhalb der Hardware-Gruppen mehr.
• Dynamische Lastenreduzierung: Wenn nach 10 Schritten 80 % deiner Strahlen den leeren Hintergrund oder den blickdichten Kern getroffen haben, arbeitet die GPU im 11. Schritt nur noch mit den verbleibenden 20 % der Daten. Ein Standard-Kernel müsste das gesamte Grid bis zum bitteren Ende durchrechnen.
